# Контур — паспорт данных IEK × Systeme Electric

Документ для команды: какие входы хранить, какие решения показывать менеджеру и как проверить ML на двух предоставленных архивах. Срез источников — **22 сентября 2026 года**. Числа ниже получены из файлов пользователя; прогнозы и метрики отдельно обозначены как результаты расчёта. Это не описание синтетического демо.

## 1. Что уже работает

В приложении появилась стартовая страница **«Данные партнёров»**: переключение IEK / Systeme Electric, поиск по коду 1С, артикулу и названию, карточка исходных данных, график продаж, прогноз позиции или всей компании, качество относительно базовой модели, сохранённые расчёты и CSV. Кнопки **«Ручной ввод»** и **«Уточнить данные»** позволяют создать позицию или дополнить существующую.

Все SKU обоих архивов сохранены. Исходные XLSX, ZIP и заполненные строки всех листов сохраняются локально. Отдельная база партнёров не смешивается с синтетическим дневным демо. В архиве не хватает части условий закупки: поэтому система выдаёт прогноз и конкретный список уточнений, а не подставляет придуманные остатки, цены или сроки поставки.

### Почему два отчёта продаж не складываются

Месячный отчёт и динамика описывают пересекающуюся деятельность. Их сложение удвоит продажи. Из-за обнаруженных расхождений текущий адаптер использует **месячный отчёт как явную основу прогноза**, динамику — для сверки, возвратов и просмотра документов. Возможные причины расхождений (фильтры, статус документов, область складов, момент проведения) требуют ответа владельца выгрузки; система не объявляет одну версию доказанно правильной.

## 4. Контракт входов: что должен хранить SaaS

| Группа | Поля | Наличие в примерах / поведение |
|---|---|---|
| Идентичность | `company`, `sku`, `supplier_sku`, `name`, `unit`, `category` | Категория есть лишь в части Systeme; неизвестные поля — `null`. Категория служит контекстом, не подставляет скрытые параметры закупки. |
| Срез | `snapshot_date` | Для данного адаптера фиксирован по архивам: `2026-09-22`. Ручной ввод позволяет изменить. |
| Месячные продажи | `monthly_sales[].month`, `quantity` со знаком | Основной источник прогноза. Не дробим месяцы на выдуманные дневные сделки. |
| Подтверждённые исключения | `monthly_sales[].excluded_quantity` | Ввод менеджера для размеченного разового объёма. Не больше положительного чистого объёма месяца. По умолчанию нет подтверждённых исключений. |
| Наличие | `monthly_sales[].stockout_days` | Только вручную подтверждённое число дней отсутствия в месяце. В примерах таких интервалов нет; месячные остатки их не заменяют. |
| Движения | дата, SKU, склад, документ, количество, исходная строка | Возвраты остаются отрицательными. Полный тип документа и исходное время сохранены в raw-слое. |
| Остаток | `stock`, `stock_date`, `stock_scope_confirmed` | Свободный запас на дату расчёта; должно быть подтверждено соответствие продажам, поступлениям и единицам. Неизвестный остаток не равен нулю. |
| Поступления | `inbound[].quantity`, `eta`, `reference` | Учитываются только поступления внутри горизонта покрытия. Просроченные ETA требуют уточнения. |
| Закупка | `moq`, `pack_size`, `purchase_price`, `lead_days` | MOQ и кратность — разные ограничения. ETA уже заказанной партии не даёт срок новой поставки. Цена неизвестна: сумма заказа остаётся пустой. |
| Политика | `review_days`, `service_level`, `growth_pct` | Явный ввод менеджера; настройки категории можно перенести сюда после подтверждения. `growth_pct` — дополнительный сценарий сверх тренда модели; **0 надо указать явно**, если дополнительный рост не нужен. |
| Материальная ведомость | `materials[].quantity`, `due_date`, `reference` | В архивах нет; форма поддерживает дополнительный проектный спрос. Менеджер подтверждает, что его нет в регулярном прогнозе. |
| Происхождение | `provenance`, `source_snapshot`, SHA-256 файла/архива, raw-строки | Сохраняем исходные значения и координаты. Ручное изменение не переписывает оригинал. |
| Аудит | версия записи, время, причина, значения до/после | Защита от перезаписи устаревшей карточкой (HTTP 409), сохранённые входы каждого расчёта. |

Для полноценной автоматизации исходного кейса дополнительно нужны: стабильный обезличенный ID клиента, признак типа операции/возврата и связь с исходной продажей, ежедневное наличие или интервалы stockout, единый складской контур, справочник сроков поставки и конверсий единиц, подтверждённая закупочная цена, материальная ведомость с признаком уже учтённого спроса. Персональные данные клиентов загружать не нужно.

## 5. Какие рекомендации должен получать менеджер

1. **Проверка входов:** «Уточните текущий свободный остаток», «Подтвердите складской контур», «Укажите срок новой поставки», а не фиктивное количество заказа.
2. **Регулярный прогноз по SKU:** помесячный спрос, выбранная модель, учтённые ручные исключения и stockout, отличие факта от прогноза.
3. **Рекомендованный заказ:** поставщик, код, количество в единице учёта, MOQ/кратность, сумма только при известной закупочной цене.
4. **Обоснование:** спрос горизонта + страховой запас + дополнительная ведомость − свободный остаток − своевременные поступления. Компоненты доступны в результате API.
5. **Срочность:** первый расчётный день дефицита, риск до прибытия новой поставки, необходимость ускорить поступление. Дневное распределение месячного спроса — явно обозначенное приближение.
6. **Качество:** WAPE/MAE на отложенных месяцах и WAPE простого среднего. Если модель хуже базовой, показать предупреждение и проверку менеджером.
7. **Аномалии:** крупные документы для расследования. Без ID клиента нельзя доказать разовую покупку конкретного клиента; автоматическое исключение всех больших отгрузок разрушит сезонный спрос.
8. **Прослеживаемость:** файл/лист/строка, версия входов, дата расчёта и история правок; результаты разделены по производителю и выгружаются как черновик.

Текущая форма работает на уровне отдельного SKU. Массовое применение политик категорий, подтверждение заказов по партнёрским данным и интеграция записи в 1С — следующие этапы. CSV уже содержит код 1С, артикул, единицу и обоснование, но его совместимость с конкретной обработкой 1С ещё нужно проверить на стороне партнёра. Отправки поставщику в этом модуле нет. В дневном демо отдельно остаётся сценарий ручного утверждения.

## 6. Алгоритм и честная оценка ML

Стек сохраняется компактным: **React + TypeScript / FastAPI + Pydantic / NumPy + scikit-learn / SQLite / openpyxl**. Отдельный адаптер превращает исходные книги в версионируемые записи; прогноз и планирование не зависят от React. Оригиналы и raw-слой позволяют проверить каждое преобразование.

Кандидаты для месячных рядов: среднее последних 3 или 6 наблюдений, тот же месяц прошлого года, Ridge с линейным трендом и годовой синусоидой, профиль производителя по завершённым годам. Годовой профиль из отчётов сезонности имеет денежный/агрегированный характер; это кандидат сезонной формы, **не** цена и **не** количественная история SKU. Готовые коэффициенты Excel, включающие 2026 год, не подаются в исторический backtest.

При 32 месяцах модели сравниваются по MAE на двух внутренних окнах: декабрь 2025 — февраль 2026 и март — май 2026. Итоговая проверка — **июнь–август 2026**, эти месяцы не выбирают модель. После проверки выбранная модель переобучается на всех доступных полных месяцах и прогнозирует сентябрь 2026 — март 2027. Для коротких рядов предусмотрены минимальные требования и fallback; полностью неизвестные месяцы не становятся обучающими нулями.

Возвраты не превращаются в положительный спрос. Месячное отрицательное нетто сохраняется в факте, для регулярного спроса используется нижняя граница 0. Это приближение: привязки возврата к исходной продаже нет. Подтверждённый разовый объём вычитается вручную; частичный stockout компенсируется по доле дней доступности. Полностью отсутствовавший месяц исключается из известных наблюдений; его скрытый объём не объявляется измеренным. Месяцы с ручной stockout-компенсацией исключаются из метрик факта.

Планирование: горизонт = срок поставки + период пересмотра. Месячный прогноз равномерно распределяется по календарным дням; страховой запас оценивается через ошибку прогноза и заданный уровень сервиса. Это приближение на короткой контрольной выборке, без гарантии фактического уровня сервиса. Затем добавляется ведомость, вычитаются доступный запас и своевременные поступления, результат округляется с учётом MOQ и кратности. Прирост применяется явно поверх модели, поэтому не копируйте туда уже учтённый исторический рост без проверки.

| Systeme / шт | 554 | 25,76% | 30,49% |

Оценены **2 453 SKU IEK и 554 SKU Systeme**. Остальные позиции сохранены, но истории нет либо она недостаточна. До ручных уточнений количество заказа не рассчитывается ни для одного SKU: модель не выдумывает отсутствующие условия. Агрегированное улучшение не означает, что каждая позиция стала лучше. Это оценка зарегистрированных чистых отгрузок на одном трёхмесячном периоде, не доказанная экономия денег, не точность скрытого спроса и не полноценная проверка обнаружения разовых клиентов.

## 7. Два конкретных примера из файлов

### IEK: `200400085_`, артикул `LC1-C5E04-311`

`F/UTP (24 AWG), кат.5Е экран, 4 пары, серый 305м ITK`, единица **м**. Месячные продажи: июнь 2026 — **4 980**, июль — **2 770**, август — **1 800**; в неполном сентябре — **605**. Источник: месячные продажи IEK, `Лист_1`, строка 3, столбцы AF:AI. Из отдельного файла минимальная отгрузка — **1**; кратность закупки не задана.

Расчёт выбрал среднее 3 месяцев: полный месячный прогноз сентября — **3 183,33 м**. Это производная величина, а не цифра из Excel. WAPE на июне–августе — **64,71%**, совпадает с базовой моделью. Количество заказа отсутствует: нужен текущий запас, согласованная кратность/единица закупки и условия поставки. Число «305м» из названия не назначается автоматически кратностью.

### Systeme: `300200428_`, артикул `ATN000343`

Розетка ATLAS алюминий, единица **шт**. В файле «Товар в пути», `TDSheet`, строка 3: категория **1**, «СС реал» **1 050,61**, AZ свободный остаток **1 118**, AY резерв **0**, AU **6**, AW **50**. Эти складские показатели не суммируются автоматически. Кратность из отдельного файла — **10**; MOQ неизвестен. Месячные продажи, `Лист_1`, строка 27: июнь — **310**, июль — **135**, август — **124**, неполный сентябрь — **81**.

AR3 содержит рост **−0,4085239**, AS3 — сезонное изменение **0,4251559**. Формулы вычисляют отношение минус 1: это дельты, а не готовые множители 0,425 или готовый будущий прирост. Исходные значения сохранены для сравнения, не добавлены второй раз к прогнозу.

Модель выбрала исторический профиль производителя; прогноз полного сентября — **280,66 шт**. Но WAPE на отложенном периоде **97,49%**, у простого среднего **50,62%** — конкретная позиция, где модель хуже baseline и требует проверки. Такой результат нельзя скрывать за средним улучшением портфеля. Остаток 1 118 сам по себе не позволяет обосновать заказ без срока, политики и подтверждения области складов.

## 8. Как воспроизвести и протестировать

Из корня проекта:

```bash
make install
.venv/bin/python -m scripts.import_partners \
  --iek '/Users/dimash/Downloads/IEK.zip' \
  --systeme '/Users/dimash/Downloads/Systeme electric.zip'
make partner-benchmark
make build
make api
```

Открыть `http://127.0.0.1:8000`. В текущем рабочем каталоге оба архива **уже импортированы**, повторять импорт не нужно. Повторный импорт существующей компании отклоняется: это защищает исходную версию и ручные изменения. Для независимого эксперимента задайте другой `EKT_PARTNER_DB` и отдельные `--sources` / `--reports` у импортера (см. `--help`); не удаляйте рабочую базу с исправлениями.

Локальные артефакты:

- `data/partners/partners.sqlite3`: справочники, движения, все исходные строки, ручные версии, сохранённые расчёты с входами.
- `data/partners/sources/iek/` и `systeme/`: неизменённые XLSX и `original.zip`.
- `data/partners/iek-audit.json`, `systeme-audit.json`: состав файлов, количества, координаты расхождений, хеши.
- `data/partners/benchmark.json`: последний backtest на фактически импортированных/уточнённых данных. Числа в разделе 6 зафиксированы для оригиналов; после ручных правок сравнивайте новый отчёт отдельно.

`data/` исключён из Git. Реальные файлы не отправляются во внешние модели. Объём данных — локальный прототип, без многопользовательской авторизации; перед размещением SaaS понадобятся аутентификация, разграничение компаний, PostgreSQL, фоновые задания и политика хранения.

### Ручной сценарий

1. Выбрать производителя и найти SKU. Сверить факты и источник в карточке.
2. Нажать «Уточнить данные». Известные поля заполнены из файлов; неизвестные пустые. Не менять их на нули ради прохождения валидации.
3. Внести согласованные остаток/дату, срок, период пересмотра, сервис, MOQ/кратность, дополнительный прирост. При необходимости уточнить поступления и ведомость.
4. В месячной истории подтвердить разовый объём и дни отсутствия только по имеющимся основаниям. Отрицательное чистое количество допустимо.
5. Подтвердить общую область складов/единиц и отсутствие двойного учёта ведомости, указать причину правки, сохранить.
6. Нажать «Прогноз позиции». Изучить формулу, качество, риски и экспортировать черновик. Сохранённый старый расчёт остаётся привязан к старым входам.

Проверки:

```bash
make test
make lint
make build
make partner-benchmark
```

Тесты логики проверяют знак возвратов, исключение неполного месяца, отсутствие утечки из holdout/будущей сезонности, компенсацию подтверждённого stockout, исключение размеченного проекта, влияние остатков/ETA/ведомости/прироста/упаковки, запрет выдуманного заказа, валидацию ручного ввода, конфликт версий и неизменяемость сохранённого расчёта. Контролируемые тестовые значения из unit tests **не используются как партнёрские данные**. Отдельная проверка реального импорта выполняется при наличии приватной базы, в чистом CI пропускается.

### API

- `GET /api/partners` — аудит обоих источников.
- `GET /api/partners/{company}/products?search=...&limit=30&offset=0` — каталог.
- `GET /api/partners/{company}/product?sku=...` — все поля, происхождение, документы, версия и история правок.
- `POST /api/partners/{company}/manual` — полная ручная версия записи; для существующей нужен `expected_version`, для новой — `null`.
- `POST /api/partners/{company}/calculate` — `{ "limit": 4000 }` для компании либо `{ "skus": ["300200428_"] }` для выбранных позиций.
- `GET /api/partners/{company}/runs` и `/runs/{id}` — сохранённые расчёты.
- `GET /api/partners/{company}/runs/{id}/export` — CSV UTF-8 с BOM, разделитель `;`, защита от формул в текстовых ячейках.

`company` — `iek` или `systeme`. Схемы ручного запроса доступны в `/docs`. Нет endpoint автоматической отправки заказа поставщику.
